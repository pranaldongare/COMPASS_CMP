# 0001. No ORM: hand-written SQL and raw-SQL migrations

Status: accepted. Dates from the first commit. Amended 2026-09-22: two
migrations backfill in Python (below).

## Context

The schema is the product. What makes a consent record worth anything is a
set of constraints, triggers and revoked grants that an object-relational
mapper cannot express and, in autogenerated migrations, does not preserve.
The exact type of a column, the text of a CHECK, the existence of a trigger:
none of these appear in a diff of model classes.

## Decision

Every query is SQL written by hand over psycopg 3, with values bound as
parameters. Every Alembic migration is raw DDL in both directions. There is
no model layer; repositories return rows as dictionaries and the domain
services work on those.

The only interpolated fragments are validated identifiers: a sort column
checked against a per-route allow-list, a scope predicate chosen by an enum.
Ruff's injection rule is suppressed only in the repository directory, so a
query appearing anywhere else still fails lint.

## Consequences

- The migration is the schema. Reading `migrations/versions/` in order is
  reading the truth, with nothing in between.
- A new column is three edits: the migration, the repository's select list,
  and the response model. Nothing fills them in for you.
- Enum drift is caught by a test that compares the Postgres types to the
  Python enumerations in both directions.
- Reviewers read SQL. That is a cost for people who have not, and a benefit
  for anyone who has been asked "what does this actually do to the table".

## Revisit when

A second consumer of the schema appears that needs a model layer, or the
repository count grows past what one person can hold. Neither is close.

## Amended · 2026-09-21 and 2026-09-22

Two migrations are not raw SQL throughout. 0028 (2026-09-21) and 0030
(2026-09-22) fill columns whose values are keyed hashes under
`BLIND_INDEX_KEY`, a key the database does not hold, and 0030 must first open
names that are already sealed, through the key service. So their backfills are
Python: each imports the application's own `cmp.infrastructure.dkms.blind`
and `client.unseal_values_sync`, so the migration and the code agree on every
hash, and writes row by row inside the migration's transaction. The DDL around
them is still SQL, and every other migration is still raw DDL in both
directions.

What this costs: those two migrations depend on application code as it stands
when they run, on the environment's `BLIND_INDEX_KEY`, and on a reachable key
service wherever sealed values exist. "Reading `migrations/versions/` is
reading the truth" still holds for the schema, not for the values those two
wrote. See [ADR 0017](0017-lookup-by-keyed-hash-and-name-ngrams.md) and
[migrations.md](../database/migrations.md).
